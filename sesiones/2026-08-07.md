## 6. Bug: "cuando estoy aqui y reinicio se pone en modo obscuro todo y tambien le pasa a los demas"

El panel se veía en modo oscuro al recargar la página, en cualquier sección, aunque el valor por defecto en código era `'light'`.

## 7. "pero el boton nunca fue tocado"

El usuario aclaró que el botón de tema (sol/luna) nunca se había tocado, descartando que la causa fuera una preferencia guardada en `localStorage`. Se investigó más a fondo y se encontró la causa real: en `globals.css`, la regla `:root, [data-admin-theme="dark"] { ... }` agrupaba las variables del tema oscuro **dentro del mismo bloque que `:root`**, lo que las convertía en el valor por defecto antes de que cualquier script de inicialización pudiera aplicar el atributo correcto. Se corrigió separando los bloques: `:root, [data-admin-theme="light"]` quedó como el bloque por defecto, y `[data-admin-theme="dark"]` quedó aparte. También se ajustó la visibilidad por defecto de `.ad-icon-dark` / `.ad-icon-light` / `.ad-logo` para que coincidiera con "claro" como estado por defecto.

Por separado, también se encontró que `app/components/AdminNav.tsx` usaba `<a href>` normal en los enlaces del sidebar en vez de `<Link>` de Next.js, causando **recargas completas de página** en cada clic de navegación — cada recarga completa volvía a ejecutar el script de tema desde cero, lo que en la práctica se sentía como que el tema "se reiniciaba" al navegar. Se convirtió a `<Link>` preservando las props de drag-and-drop del sidebar reordenable.

## 11. Especificación completa del asistente de bienvenida (onboarding wizard)

El usuario pegó una especificación detallada: cuando un restaurante entra a `/admin` por primera vez, debe verse un asistente de 3 pasos (nombre → logo → colores) antes de poder usar el resto del panel, y ese asistente debe guardar en las mismas claves de `settings` que ya usa `/admin/configuracion`, para poder seguir editando después desde ahí con normalidad.

Se construyó:
- **`middleware.ts`** — nueva función `isOnboardingComplete()`, compatible con Edge Runtime (fetch directo a la REST API de Supabase, igual que el patrón de `lib/birthdayDb.ts`, en vez del cliente `supabase-js`). Consulta las claves mínimas de identidad y, si falta alguna, redirige cualquier ruta `/admin/*` (excepto `/admin/login`) a `/admin/onboarding`; si ya está completo y el usuario visita `/admin/onboarding`, lo regresa a `/admin/menu`. Falla abierto (no bloquea) si Supabase no responde — es un gate de onboarding, no la autenticación real.
- **`app/admin/onboarding/page.tsx`** (nuevo) — wizard de 3 pasos con barra de progreso: Nombre del restaurante → Logo (dropzone con drag & drop, usa `uploadWebp()`) → 3 colores con vista previa en vivo. Al finalizar, guarda cada campo vía `POST /api/settings`.

## 25. "que pedo con el logo y checa mas errores y arrreglalos o bugs" — bug del logo roto + auditoría (trabajo de hoy)

Captura de la vista previa de "Logo del restaurante" en `/admin/configuracion` mostrando el ícono de imagen rota, y el sidebar del admin mostrando un logo genérico distinto al real. Se investigó a fondo y se encontraron **dos causas raíz distintas**, encadenadas:

**Causa 1 — `menu_logo` nunca se llenó para este restaurante.** La consolidación del punto 24 cambió los 3 layouts para leer *solo* `menu_logo`, sin caer de vuelta a `profile_logo`. Pero el asistente de bienvenida (`app/admin/onboarding/page.tsx`, punto 11) seguía guardando el logo en la clave vieja `profile_logo`, no en `menu_logo` — así que para `menu-demo`, `menu_logo` estaba vacío y el sidebar caía al logo hardcodeado por defecto (`/logo.png`) en vez del logo real subido por el usuario. Confirmado con una consulta directa a la tabla `settings` en Supabase.

**Causa 2 — el logo guardado era un SVG servido con `Content-Disposition: attachment`.** El `profile_logo` real apuntaba a un `.svg` en el bucket `uploads/` de Supabase Storage. Confirmado con `curl -I` que Supabase sirve los SVG subidos con el header `Content-Disposition: attachment`, lo que hace que el navegador intente **descargar** el archivo en vez de renderizarlo dentro de un `<img>` — de ahí el ícono de imagen rota en la vista previa de configuración. Se comparó con un `.webp` de la misma sesión, que no tiene ese header.

### Correcciones aplicadas

1. **`lib/uploadWebp.ts`** — se quitó el caso especial que dejaba pasar los SVG sin convertir; ahora **todo** archivo subido (incluyendo SVG) se rasteriza a WebP vía Canvas API antes de subirse, evitando que vuelva a pasar con subidas futuras.
2. **Fallback `menu_logo || profile_logo`** restaurado en los tres layouts de servidor (`app/admin/layout.tsx`, `app/employee/layout.tsx`, `app/resta3/(panel)/layout.tsx`) y en las tres páginas de login (`app/admin/login/page.tsx`, `app/employee/login/page.tsx`, `app/resta3/login/page.tsx` — esta última también corregida para leer `resta3_accent`/`menu_hover_color` y `resta3_logo`/`menu_logo`/`profile_logo` en vez de las claves legacy sueltas que traía).
3. **Reconversión del archivo roto ya existente.** El fix de `uploadWebp.ts` solo evita el problema en subidas *futuras* — el SVG ya subido seguía roto. Se escribió un script de Node que descarga el SVG (`693 bytes`), lo rasteriza a WebP con `sharp` (512×512, calidad 90 → `5868 bytes`) y lo vuelve a subir a Supabase Storage; se confirmó con `curl -I` que el nuevo `.webp` **no** tiene `Content-Disposition: attachment`. Se actualizó la clave `menu-demo:menu_logo` para que apunte a este nuevo archivo.
4. **Corrección de raíz en el asistente de bienvenida** (`app/admin/onboarding/page.tsx`) para que futuros restaurantes no repitan el mismo bug: ahora guarda directamente en `menu_logo` (no `profile_logo`) y remapeó los 3 colores del wizard a las claves reales que usa "Identidad del restaurante" — primario → `menu_hover_color` (antes iba a la clave huérfana `sidebar_accent`), secundario → `menu_btn_color` (sin cambio), terciario → `menu_bg_color` (antes se guardaba, de forma redundante, otra vez en `menu_hover_color`). Se ajustaron las etiquetas/pistas del paso 3 y la vista previa en vivo del wizard para reflejar el nuevo mapeo (el color terciario ahora se ve como un fondo, no como una pastilla de texto "Acento").
5. **`middleware.ts`** — el gate de onboarding exigía las claves legacy exactas (`profile_logo`, `sidebar_accent`). Cambiarlas de raíz por las nuevas (`menu_logo`, `menu_bg_color`) habría roto el gate para restaurantes ya existentes que completaron el onboarding con las claves viejas y nunca las volvieron a tocar — en particular **portales**, que solo tiene `profile_logo`/`sidebar_accent` seteadas. Se optó por una verificación más tolerante: `restaurant_name` y `menu_btn_color` siguen siendo obligatorios, pero para el logo y el acento se acepta **cualquiera** de las dos claves (vieja o nueva) mediante grupos OR (`ONBOARDING_KEY_GROUPS`), sin forzar a portales de vuelta al asistente.
